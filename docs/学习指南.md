## 1. 数据表设计（第 1、3、4 步）

```
users ──< terms
  │         │
  │         └──< record_terms >──┐
  └──< records ──────────────────┘
  └──< sessions
```

- **terms（用语）**：japanese / chinese / reading / category / note，再加上 user_id。
  - 读音统一存成平假名 → 用户输入片假名也能搜到。
  - `(user_id, japanese, chinese)` 有唯一约束：同一个人不能重复登记同一对译词，但"同一个日语对应多个中文译法"是允许的（分别登记）。
- **records（对应记录）**：标题、日期、手续类型、状况、卡在哪里、怎么解释的、下次改进。
  - "卡在哪里"和"怎么解释的"设为必填 —— 这是这个功能存在的意义。
- **record_terms（中间表）**：一条记录可以用到多个用语，一个用语也会出现在多条记录里 → 多对多 → 需要中间表。
  - `ON DELETE CASCADE`：删掉记录或用语时，关联自动删除，不会留下"指向不存在数据"的垃圾行。
- **类别为什么没有单独建表？** 个人使用、种类少、想随时自由新增。代价是"改类别名"要批量更新。面试时可以说"考虑过，权衡后选择了简单的方案"。

## 2. 检索（第 2 步）——面试最好讲的地方

处理流程（`src/app/terms/queries.ts` 的 `searchTerms`）：

1. 用户输入 → `normalize()`（NFKC 规范化：全角英数→半角、半角片假名→全角）
2. 按空格切成多个关键词（全角空格也算）
3. 每个关键词：日语 / 中文 / 读音 / 备注 **任意一列包含就算命中（OR）**
4. 多个关键词之间：**全部都要命中（AND）**
5. 读音列用平假名版的关键词去比较
6. `%` `_` 这些 LIKE 的通配符要转义，否则搜 "100%" 会匹配到所有数据

检索条件放在 URL（`/terms?q=...&category=...`）里，所以可以收藏、分享、浏览器"后退"也能正常工作。

### 建议你自己动手改的地方（选一两个就够）

难度从低到高：

1. **把"类别"也加进关键词检索范围**
   在 `searchTerms` 的 `or(...)` 里加一行 `ilike(terms.category, p.text)`。改完想一想：这样做的好处和坏处是什么？（提示：搜"契约"时结果会变多）
2. **简繁体都能搜到**（例如输入「证明」也能搜到登记成「證明」的词）
   思路：做一个小的简繁对照表，检索前把关键词转换出两种写法，都去搜。这正好是你作为中日通译才会想到的点，面试时非常有说服力。
3. **检索结果按"命中程度"排序**（日语完全一致的排在最前面）
   提示：`orderBy` 里用 `sql\`${terms.japanese} = ${keyword}\` desc`。

改完后跑 `npm test` 和 `npm run lint`，并在 `src/lib/search.test.ts` 里加一个测试。

## 3. 登录（第 4 步）

- **密码**：用 Node.js 自带的 scrypt 做哈希（加盐）。数据库里只有哈希值，看不到原密码。比较时用 `timingSafeEqual`（常数时间比较），防止通过响应时间推测密码。
- **会话（session）**：登录成功后生成一个随机字符串（token）放进 Cookie。
  - Cookie 设置了 `httpOnly`（JS 读不到，防 XSS 盗取）、`SameSite=Lax`（别的网站发来的 POST 不带 Cookie，防 CSRF）。
  - 数据库里只存 token 的 SHA-256 哈希，即使数据库泄露也不能直接拿来登录。
- **数据隔离**：每个页面、每个 Server Action 开头都调用 `requireUser()`，SQL 的 where 条件里**一定**带 `user_id`。
  - 实测过：登录另一个账号，直接在 URL 里改成别人用语的 ID → 404。
  - 对应记录关联的用语 ID 也会在服务器端检查"是不是自己的用语"，防止有人改 HTML 里的隐藏字段。
- **为什么不用 NextAuth / Supabase Auth？** 为了理解原理而自己实现。真正的业务中更推荐使用成熟的库或服务（面试时这样说比较稳妥）。

## 4. CSV（第 5 步）

- **文字编码**：按 UTF-8 → Shift_JIS → GB18030 的顺序尝试解码。
  - 实际踩到的坑：**Shift_JIS 里根本没有很多简体字**（证、师……），日文版 Excel 用"CSV"格式保存时中文会变成"?"。所以页面上提示用"CSV UTF-8"格式保存。这是很好的"遇到的问题"素材。
- **全部导入或全部不导入**：只要有一行出错就一条都不导入，并显示"第几行、什么错误"。因为导入一半的话，用户不知道哪些进去了、哪些没进去。
- **重复处理**：已存在的用语可以选"跳过"或"覆盖"。文件内同一个用语出现两次时，以后面的为准 —— 因为 PostgreSQL 的 `ON CONFLICT DO UPDATE` 不能在一条语句里更新同一行两次（会报错）。
- **导出**：带 BOM 的 UTF-8，用 Excel 双击打开也不会乱码；以 `=` `+` 开头的单元格前面加 `'`，防止在 Excel 里被当作公式执行（CSV 注入）。

## 5. 部署（第 6 步）——需要你自己操作

1. 在 Neon（https://neon.tech）注册，新建项目，复制连接字符串
2. 本地执行：`DATABASE_URL=<连接字符串> npm run db:migrate`，想要演示数据再执行 `npm run db:seed`
3. 在 Vercel 导入这个 GitHub 仓库，环境变量里设置 `DATABASE_URL`，点 Deploy
4. 把网址写进 README 的「デモ」那一行

## 6. 面试可能被问的问题

| 问题                               | 回答要点                                                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 为什么做这个？                     | 自己通译现场的问题：同样的手续反复卡住，说明方法只在自己脑子里 → 用机制解决                                     |
| 最费功夫的地方？                   | 检索的表记ゆれ / Shift_JIS 简体字问题 / 用户数据隔离，选一个讲具体                                              |
| 怎么保证别人看不到我的数据？       | 所有查询都带 user_id；服务器端检查；实际改 URL 测试过                                                           |
| 为什么选 PostgreSQL 而不是 NoSQL？ | 多对多关系、唯一约束、事务（CSV 导入要全部成功或全部失败）                                                      |
| 用户和用语数量变成 10 万条怎么办？ | 现在用 LIKE '%...%' 不能用普通索引 → 可以加 pg_trgm 的 GIN 索引；分页已经做了                                   |
| 测试怎么做的？                     | 规范化、检索、CSV、密码这些纯函数用 Vitest 写了单元测试；画面用浏览器手动确认；GitHub Actions 每次 push 自动跑  |
| AI 用了吗？                        | 如实说：用 AI 辅助生成代码，但每一步的设计都自己确认、理解，并自己改了检索部分（所以一定要真的改一下第 2 步！） |
